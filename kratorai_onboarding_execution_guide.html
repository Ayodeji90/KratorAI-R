Phase 1 Foundation — Brand Intelligence Profile structure Days 1–3 · Before any UI ▾
Goal: Define the data structure your entire product reasons from. Nothing else gets built until this is locked. Every screen, every AI call, every enrichment loop feeds into or reads from this object.
Tasks
1.1
Define the Brand Intelligence Profile schema
Create the full JSON schema: Brand Identity, Offering Map, Audience Profile, Voice Fingerprint, Point of View, Competitive Context, Content Parameters, Performance Intelligence. Every field name, type, and whether it's required or optional. Include a confidence_score per field (0–1) that starts low and rises as more evidence accumulates.

1.2
Define the Voice Fingerprint sub-schema
Formality (1–5), warmth (1–5), humor (none/occasional/frequent), emoji usage (none/minimal/moderate/heavy), caption length preference, cultural register (free text), signature phrases (string array), never-use list (string array), live voice sample (verbatim string), running approved samples (last 5, string array). This sub-schema is read on every single content generation call — get it right before anything else.
DevAICritical path
1.3
Build the profile write and read API
Simple endpoints: create profile, update field(s), read full profile, read specific fields. Must support partial profiles (not all 14 questions answered yet) — partial profiles are used for the mid-onboarding wow moment. Write tests before any UI touches this.
Dev
1.4
Map each of the 14 onboarding questions to profile fields
A clear document showing: question number → which profile field(s) it populates → how the raw answer gets transformed (verbatim storage vs structured extraction vs AI-parsed summary). Some questions populate multiple fields. Question 4 (live voice sample) populates the Voice Fingerprint verbatim — it must never be summarised or processed.

Phase 2 AI conversation engine — the two-way brain Days 2–5 · Parallel with Phase 1 ▾
Goal: Build the AI layer that conducts the onboarding as a real conversation — asking questions, acknowledging answers, transitioning naturally. This is the core product experience. The UI wraps this; it does not drive it.
Tasks
2.1
Write the master onboarding system prompt
This prompt tells the AI: you are conducting a brand discovery conversation for KratorAI. Your job is to ask the 14 questions in sequence, acknowledge each answer before moving to the next, adapt your transition based on what was said (if they mention a competitor in Q1, reference it in Q10), handle tangents by capturing the signal and redirecting gracefully, never use numbered question labels. Include the full question list with their extraction intent, the transition guidelines, and examples of good vs bad acknowledgements.
AIProductCritical path
2.2
Build the conversation state manager
Tracks: which questions have been answered, what has been extracted so far, the full conversation transcript, and the partial Brand Intelligence Profile. The state is passed into every AI call so the conversation has memory. On each turn: AI receives full state + user's latest message, returns next question + profile field updates.
DevAI
2.3
Build the profile extraction parser
After each user response, a secondary AI call (lightweight, fast) extracts the structured data and writes it to the profile. This runs asynchronously — the user sees the conversation flowing while the extraction happens in the background. Define the extraction prompt per question: Q3 extracts product name + price pairs, Q5 extracts verbatim phrases as an array, Q4 stores the exact text with no modification.
DevAI
2.4
Test the conversation for naturalness — manually, not with metrics
Every team member goes through the full 14-question onboarding as if they are a Nigerian business owner. Note every moment it felt like a form rather than a conversation. Note every acknowledgement that felt generic or robotic. Note every transition that felt abrupt. Fix these in the system prompt before any UI work begins. The bar is: it should feel like talking to a smart brand consultant who genuinely wants to understand your business.

Phase 3 Voice + type input system Days 4–7 ▾
Goal: Build the mixed-mode input layer. Voice is the ambient default for personality questions. Type is the default for precision questions. The user never makes a binary "voice or type" decision — the interface handles it invisibly.
Tasks
3.1
Assign input mode to each of the 14 questions
Voice default: Q1, Q2, Q7, Q8, Q9, Q14. Type default: Q3 (products/prices), Q5 (signature phrases), Q10 (competitors), Q12 (guardrails), Q13 (posting frequency). Hybrid (equal weight): Q4 (live voice sample), Q6 (aspirational reference), Q11 (customer's current world). Lock this list before any UI implementation begins.
ProductDesign
3.2
Implement voice capture with real-time transcription
Use Web Speech API or a library like Whisper-based transcription. Key requirements: microphone activates automatically when a voice-default question appears (no button press to begin), transcription appears in real time in an editable text field, the field is large and readable, the user can edit the transcription before confirming. Visual listening indicator must not resemble a recording button — it should feel ambient, not performative.
DevCritical path
3.3
Build the quiet mode toggle
Small, unobtrusive toggle below the listening indicator for voice-default questions: "prefer to type instead?" And below the text field for type-default questions: "prefer to speak instead?" The toggle is available but not prominent. It must never be the first thing the user sees on any question screen. Test that switching modes mid-answer carries the content across (partial transcription becomes the starting text in the type field).
DevDesign
3.4
Handle tangents in voice input
When a user speaks beyond the scope of the current question, the system should not cut them off. All spoken content is captured. The conversation AI then acknowledges what they said, extracts any relevant brand signal from the tangent into the appropriate profile fields, and naturally returns to the current question. This requires the parser (2.3) to scan for off-question brand signals in every turn.

Phase 4 The mid-onboarding wow moment Days 6–8 · Highest priority feature ▾
Goal: After question 4, generate one piece of sample content in real time and show it inside the onboarding flow. This converts a leap of faith into demonstrated proof and is the single most important activation moment in the product.
Why this is non-negotiable: Without this moment, the user completes onboarding on faith alone. With it, they have seen evidence by question 5. Onboarding completion rates and first-week retention will measurably differ with vs without this feature. Build it before anything decorative.
Tasks
4.1
Build the partial-profile generation prompt
A generation prompt specifically designed for partial profiles (Q1–Q4 complete). The prompt must: acknowledge that the profile is partial, use the live voice sample from Q4 as a few-shot example (not as a data description — as an actual style example: "generate content that matches this style: [verbatim Q4 answer]"), generate the single highest-confidence content type for the user's industry, keep the result short enough to be immediately readable on screen.
AICritical path
4.2
Design the wow moment screen
The generated content appears between Q4 and Q5 in the conversation flow. It should feel like the AI pausing to show what it has learned so far — not like a modal or an interruption. The copy around it: "Here's what KratorAI already sounds like in your voice. We're only halfway through — it gets more accurate from here." The generated content displays in a styled post preview (platform-appropriate framing). One button: "Continue" to proceed to Q5.
DesignCritical path
4.3
4.3
Measure the wow moment's impact from day one
Log: time spent on the wow moment screen, whether the user read the generated content (scroll depth or time threshold), whether they edited the generated content, onboarding completion rate after vs before this screen. These are your early signal on whether the generated content is landing. If users spend less than 5 seconds on it, the content is not landing — debug the generation prompt.

Phase 5 Confirmation screen + calendar reveal Days 8–11 ▾
Goal: After all 14 questions, show the user what KratorAI learned (editable summary), then reveal the first week of content as a designed moment — not a list.
Tasks
5.1
Build the brand summary generator
An AI prompt that takes the full Brand Intelligence Profile and generates a warm, human-readable brand summary — not a field listing, a natural-language description of the brand. Each section is editable. Every edit triggers a profile field update and is flagged as a high-confidence correction. The summary should sound like a smart brand consultant describing a client's brand after a discovery session.
AIDev
5.2
Design the confirmation screen as a reveal
Not a review form. A reveal. Visual design should give the user the sense that the system genuinely learned something about them. Each section of the summary appears as a distinct readable card. Edit mode available per section — not an "edit all" form. Tone is warm and specific: "Your brand speaks like a trusted expert — direct, warm, never generic." Not: "Formality: 2, Warmth: 4."
Design
5.3
Design the calendar reveal screen
Show the first 7 days only. Each post shows: day, platform, content type, caption preview (first 2 lines). Captions expand on tap/click to full post. The second wow moment happens when a user reads the first full caption and hears their own voice. Give captions enough space to be read. Below the calendar, the single most important line of copy in the product: "KratorAI will publish these automatically. You don't need to do anything. But you can review, edit, or approve any post before it goes out."

Phase 6 Edit-capture system — the compounding advantage Days 10–14 · Build from day one, not later ▾
Goal: Every user interaction with generated content teaches the system something. This is the mechanism that makes KratorAI irreplaceable at month 6. It must be built from the start — retrofitting it is significantly harder.
The compounding logic: At month 1, the voice is good. At month 6, it approaches uncanny — built from hundreds of micro-corrections the user made naturally, without ever being aware they were training the system. A competitor starting fresh at month 6 cannot replicate 6 months of learning.
Tasks
6.1
Build the edit diff capture system
When a user edits a generated post, store both original and edited versions. Run a diff. Extract patterns: words removed, words added, length change direction, punctuation changes, emoji additions/removals. These diffs feed into a weekly Voice Fingerprint update job that adjusts formality, length preference, and signature phrase lists automatically. No manual tagging required.
DevAICritical path
6.2
Build the approved post sample store
Every post the user approves without any edits is stored verbatim in the "running approved samples" field (rolling window of last 5). Once this field has 5+ entries, these samples should be weighted more heavily in the generation prompt than the original Q4 voice sample — they represent the most calibrated version of the brand voice to date. Update the generation prompt logic to detect when this field is populated and shift weighting accordingly.
DevAI
6.3
Build rejection pattern detection
When a user rejects a post outright (no edits, just decline), log the content type, angle, structural pattern, and tone of that post. After 3+ rejections with a shared attribute, auto-add a soft guardrail to the profile (flagged as system-derived, lower confidence than user-stated guardrails). Surface these to the user in the profile confirmation screen for approval — don't silently add hard constraints.

Phase 7 Opening screen + emotional arc polish Days 12–14 · After core systems are stable ▾
Goal: The emotional arc from anticipation through relief must be designed deliberately. Every screen is tested against the question: does this feel like a conversation or a form? Fix anything that feels like a form.
Tasks
7.1
Write and test the opening screen copy
The opening screen must: set anticipation, signal this is different, be specific about what KratorAI will learn, avoid the words "setup", "steps", "form", and "complete". The very first interaction is: "Before we start — what's your name, and what's the name of your business?" This is the first voice mode activation. Low stakes, just a name. Sets the tone before anything demanding is asked.
DesignProduct
7.2
Run the full onboarding with 5 real business owners
Not internal team members. Real business owners from your target market. Watch where they hesitate, where they seem confused, where they skip or give short answers. Every hesitation is a friction point in the design. Every short answer is a question that failed to unlock depth. Fix before launch. The bar for each question: the user gives a specific, personal answer that you could not have guessed without knowing their business.
ProductCritical path
7.3
Design and test the first automated post notification
The moment the first post publishes automatically, the user receives a notification. The copy: "Your first post just went live on [platform]. KratorAI did that while you were busy doing everything else." This is the final wow moment in the arc. It must arrive at the moment of publishing — not batched, not delayed. The post it publishes first should be the highest-confidence post in the calendar — the one most strongly reflecting the brand profile. This is a deliberate choice, not chronological.
